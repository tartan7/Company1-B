# Prisma Schema Migration Audit: PostgreSQL to MySQL/MariaDB

**Date:** 2026-05-15
**Issue:** ESC-43 (ESC-41.2)
**Scope:** Migrate all Prisma schemas from PostgreSQL to MySQL/MariaDB

## Executive Summary

This audit identifies PostgreSQL-specific features in the Escape monorepo's Prisma schemas and provides a migration plan to MySQL/MariaDB. 

**Key Finding:** The `faq-bot` service uses PostgreSQL's `pgvector` extension for vector embeddings (1536-dimensional embeddings). This is the primary blocker for MySQL migration and requires careful handling.

**Status of Services:**
- ✅ **invoice-generator-jp**: Already on MySQL (no migration needed)
- ⚠️ **faq-bot**: Uses pgvector, requires migration
- ⚠️ **dashboard**: Standard PostgreSQL, straightforward migration

---

## 1. PostgreSQL-Specific Features Identified

### 1.1 faq-bot Service (`services/faq-bot/packages/db/prisma/schema.prisma`)

#### 🔴 CRITICAL: Vector Embedding Type (Line 117)

**Current Code:**
```prisma
model Embedding {
  id          String    @id @default(cuid())
  documentId  String
  content     String    @db.Text
  embedding   Vector    @db.VectorEmbedding(1536) // text-embedding-3-small
  createdAt   DateTime  @default(now())
  document    Document  @relation(fields: [documentId], references: [id], onDelete: Cascade)
  @@index([documentId])
}
```

**Issue:** 
- PostgreSQL's `pgvector` extension with `Vector` type and `VectorEmbedding(1536)` attribute
- No native equivalent in MySQL < 8.0.35
- Vector search uses raw SQL with pgvector operators (`<=>`, `::vector`)

**Usage:**
- Embeddings generated by OpenAI (1536-dimensional vectors for `text-embedding-3-small`)
- Stored in Prisma as `Vector` type
- Queried using pgvector cosine distance in `vector-search.ts` via raw SQL

**Current Query Pattern (from `vector-search.ts`, line 38-42):**
```typescript
(1 - (e.embedding <=> ${queryEmbedding}::vector)) as similarity
FROM embeddings e
...
ORDER BY e.embedding <=> ${queryEmbedding}::vector
LIMIT ${topK}
```

#### ⚠️ MEDIUM: Array Type (Line 135)

**Current Code:**
```prisma
model Question {
  // ...
  usedDocs    String[]  // IDs of documents used for answer
  // ...
}
```

**Issue:** 
- PostgreSQL native array type `String[]`
- MySQL does not have native arrays
- Prisma ORM supports this on PostgreSQL but not MySQL

**Migration Strategy:**
- Change to JSON array: `usedDocs Json` or use TEXT with JSON.stringify/parse
- Recommended: Use JSON for structured data

#### 🟡 LOW: JSON Type (Line 184)

**Current Code:**
```prisma
model WebhookLog {
  payload   Json
  // ...
}
```

**Status:** MySQL fully supports JSON type since 5.7. **No change needed.**

## 2. Migration Strategy by Component

### 2.1 Vector Embeddings (faq-bot) - CRITICAL PATH

#### Option 1: MySQL VECTOR Type (Recommended for MySQL 8.0.35+)

**Pros:**
- Native support in modern MySQL versions
- Best performance for vector operations
- Future-proof

**Cons:**
- Requires MySQL 8.0.35+ or MariaDB 11.6+
- Vector search syntax differs from pgvector

**Implementation Steps:**
1. Change schema type: `embedding Vector @db.VectorEmbedding(1536)` (MySQL syntax may differ)
2. Update vector search query in `vector-search.ts` to use MySQL distance functions
3. Test similarity calculation compatibility

**MySQL Vector Search Syntax** (using distance_measure):
```sql
SELECT ... 
FROM embeddings e
WHERE d.bot_id = ?
ORDER BY EUCLIDEAN_DISTANCE(e.embedding, CAST(? AS JSON))
LIMIT ?
```

#### Option 2: LONGBLOB Storage (Fallback for MySQL < 8.0.35)

**Pros:**
- Works on any MySQL version
- Maximum compatibility

**Cons:**
- No native vector search
- Application-level similarity calculation required
- Performance impact for large-scale searches

**Implementation Steps:**
1. Change type: `embedding Bytes` (stored as LONGBLOB)
2. Serialize embeddings to/from binary format in application code
3. Implement cosine similarity in application (TypeScript utility function)
4. Update `vector-search.ts` to fetch all embeddings and calculate similarity in-memory

#### Option 3: JSON Storage (Hybrid Approach)

**Pros:**
- Works on all MySQL versions
- Human-readable in database
- Can use JSON functions for filtering

**Cons:**
- Larger storage footprint
- Slower than native vectors

**Implementation:** 
```prisma
embedding String @db.LongText // Store as JSON stringified array
```

| CUID | ✅ | ✅ | ✅ | No change |
| DateTime | ✅ | ✅ | ✅ | No change |
| @updatedAt | ✅ | ✅ | ✅ | No change |
| @db.Text | ✅ | ✅ | ✅ | No change |
| @db.Decimal | ✅ | ✅ | ✅ | No change |
| JSON | ✅ | ✅ (5.7+) | ✅ | No change |
| Arrays (String[]) | ✅ | ❌ | ❌ | Migrate to JSON |
| pgvector/@db.Vector | ✅ | ❌ | ✅ (8.0.35+) | See Section 2.1 |
| Cascade Deletes | ✅ | ✅ | ✅ | No change |
| Unique Constraints | ✅ | ✅ | ✅ | No change |
